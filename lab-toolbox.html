主页/专题实战 3

🧰 从零到上线自己的工具站

这一章不是虚构的练习，而是一次真实复盘：一个 20 个工具、约 10 万行访问的在线工具站 是怎么从一句"给博客读者做点小工具"长出来的。你会看到每个关键决策是怎么做的、踩了哪些坑、 哪些功夫被证明是白费的。看完你完全可以照着做自己的版本。

✅ 前置要求：已完成主页教程（会建仓库、传文件）＋ 实战 1（Pages 建站）。会用 AI 编程工具更佳。
Step 1

从一个"顺手"的想法开始

工具站的起点不是"我要做个大网站"，而是一个小到不能再小的念头：

💡 起点案例：「我博客的读者经常要查时间戳、转 JSON，每次都要去广告满天飞的在线工具站——不如自己做一个干净的，顺手挂在我域名下。」

注意这个起点有三个特征，这决定了项目能不能活下去：

  • 自己会用——做给自己用的工具最不容易烂尾，因为你自己就是第一个用户
  • 颗粒度小——"一个 JSON 格式化页面"一周内能做完，"一个开发者平台"永远做不完
  • 可生长——第一个工具做完就是完整可用的网站，之后每个工具都是增量
⚠️ 反面教材：一上来就规划"我要做 50 个工具、用户系统、会员付费"。这种规划在第一周就会把你压垮。真实路径是：先上 1 个，用起来，缺什么加什么——案例里的工具站就是这样从 1 个长到 20 个的。
Step 2

技术选型：为什么是"纯前端、零构建"

做工具站前必须回答一个问题：数据在哪处理？这决定了整个项目的命运。

🖥️ 纯前端（推荐起步）

HTML + CSS + JS，无需后端

  • 数据全部在用户浏览器里处理，天然"隐私友好"（JSON、密码这类敏感输入不出浏览器）
  • 托管成本为零：GitHub Pages / Vercel / Cloudflare 全部免费
  • 没有服务器就没有服务器要维护——不会被入侵、不用打补丁、不怕被刷流量
  • 缺点：能力边界 = 浏览器边界（做不了真正的用户系统、定时任务）
VS

🗄️ 带后端

需要服务器 / 数据库

  • 能做用户账号、数据存储、定时任务、调用 AI
  • 代价：要管数据库、防注入、防滥用、备份……每一项都是长期负担
  • 适合场景：数据需要多设备同步或需要服务端算力时再上
  • 新手陷阱：为了"显得专业"先搭后端，结果工具还没做出来先被运维劝退
✅ 实战结论：工具站 90% 的需求（格式化、转换、生成、编解码）纯前端就够。案例里唯一需要后端的"跨设备书签同步"是后来单独拆出来的另一个项目，而不是一开始就堆在工具站里。按需生长 > 一步到位。
Step 3

动手做：第一个工具的正确姿势

选一个最简单的入手——推荐 JSON 格式化，30 行代码就能用，而且立刻能自测对错。

A

先立骨架：一个页面一个工具

别急着做"工具集框架"。就一个 index.html，一个工具，能用为先。案例里的做法是后来才抽象出"标签页切换"的——当你有第 3 个工具时再抽象，抽象时机才对。

💡 经验法则：事不过三，三再抽象。重复第三次再提取公共代码，避免为不存在的需求做设计。
B

核心逻辑 30 行，剩下的是体验

JSON 格式化的核心就一句 JSON.parse + JSON.stringify。但让用户"愿意再来"，靠的是：错误提示告诉用户错在第几行、按钮点击有反馈、输入框会自动聚焦。这些"体验细节"才是工具站的护城河。

C

用 AI 编程工具加速，但自己当验收员

让 AI 生成第一版代码完全没问题，但有两件事必须自己做：① 每个功能亲手测一遍边界情况（空输入、超长输入、中文、emoji）；② 安全底线自己把关——凡是把用户输入显示到页面上的地方都要防 XSS，案例里用 DOMPurify 过滤了所有富文本渲染。

⚠️ 真实踩坑：案例中一个"复制成功"的按钮，最初在非 HTTPS 环境下静默失败（剪贴板 API 需要安全上下文）。AI 生成的代码在理想环境下都是对的，坑都在边界上。
Step 4

细节打磨：从"能用"到"愿意推荐"

工具站之间的差距，90% 在这些看不见的地方。按投入产出比排序：

A

深浅色主题 + 记住用户偏好

跟随系统 prefers-color-scheme 自动切换，用户手动选过就记住（localStorage）。这是现代网页的"及格线"。

B

离线缓存（Service Worker）

加一个几十行的 Service Worker，用户第二次访问后断网也能用。注意一个新手必踩的坑：改了代码必须递增缓存版本号，否则老用户永远拿到旧文件——案例作者忘过不止一次。

C

无障碍与细节

键盘能操作（Tab + 方向键切换工具）、状态提示用 aria-live、触控目标别小于 32px、数字用等宽字体（时间戳跳动不抖）。这些单看都是小事，加起来就是"这个站很专业"的体感。

Step 5

上线：免费、绑域名、进可在 Vercel

发布路径和 实战 1 一样从 GitHub Pages 开始，但工具站流量上来后有更优解：

A

第一步：GitHub Pages（零成本验证）

仓库 Settings → Pages → 选 main 分支。1 分钟上线，够用很久。

B

第二步：绑定自己的域名

买个域名（几十元/年），DNS 加一条 CNAME 指向你的 Pages 地址。从此 tools.你的域名.top 就是工具站入口，还自带 CDN。

C

第三步：迁 Vercel（要动态能力时）

Vercel 免费、推代码自动部署、支持 Serverless——案例的工具站后期就是这样迁的，顺带把博客、教程、其他工具全部挂成 xxx.你的域名 的子域名，形成自己的"产品矩阵"。

💡 迁移提醒：域名变更后记得全站搜索旧地址（og:url、canonical、README、页脚），漏一处就是死链。案例迁移时就靠 grep github.io 抓出了 5 处遗漏。
复盘

如果重来一次，作者会改什么

真实复盘的价值在踩坑。以下每条都有真实代价：

  • 一开始就该用单文件结构——后期 20 个工具挤在一个 HTML 里，重构花了整整一轮优化才理顺
  • 缓存版本号应该自动化——靠人肉记得改版本号，用户反馈"看不到新功能"排查了半小时，发现是自己忘了改
  • 每个工具上线前跑一遍边界清单——空输入、超长输入、中文 emoji、离线状态，四项十秒钟，能挡住 80% 的尴尬
  • 做对的事：坚持"数据不上传"的承诺（哪怕加后端能省事），是工具站最值的口碑投资

现在轮到你了。你的第一个工具是什么？任何你手动重复过三次的操作，都值得变成一个页面。
